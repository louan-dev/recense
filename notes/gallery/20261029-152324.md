# Main Gallery UI — Personal, Public & Activity

Redesign the main gallery navigation and layout to match the supplied screenshot. The goal is to make the **Personal, Public, and Activity tabs share the same visual language, layout, and interaction patterns.**

### 1. Top navigation

Replicate the screenshot's overall structure:

- Centered page title.
    
- Plus (+) action and overflow menu (...) on the right.
    
- Remove the left-facing chevron from this navigation because the existing blue back button above already performs that function.
    
- Directly underneath, use the same horizontal, rounded, three-section segmented control shown in the screenshot.
    

Rename the three tabs:

- **Personal** (currently Main)
    
- **Public** (currently Shared)
    
- **Activity**
    

Preserve the screenshot's proportions, spacing, dark background, rounded corners, typography, and selected-tab treatment, including the blue active text.

### 2. Personal tab

This is the user's private, personal collection of folders.

Display folder cards sourced from:

- **Chau's MacBook Pro** — a future location integration that has not yet been built.
    
- Folders in `/main`.
    
- Folders in `/main/archive`.
    

The MacBook Pro location should be accommodated in the architecture and UI even though its integration is not yet available.

### 3. Public tab

This replaces the existing Shared tab.

It should aggregate every share link created across all gallery locations, regardless of whether the original folder resides in:

- `/main`
    
- `/main/public`
    
- `/main/archive`
    
- Any other supported location.
    

Each share link should be represented by a folder card with a thumbnail.

The Public tab is therefore a unified collection of all publicly shared folders, rather than a view restricted to one particular directory.

### 4. Folder card layout

Both Personal and Public must use the same card design and layout.

- Two cards per row.
    
- Scrollable vertically.
    
- Each card represents a folder or share link, depending on the tab.
    
- Display a representative thumbnail from the folder's contents.
    
- Use the same rounded image-card treatment, proportions, typography, and text placement as the supplied screenshot.
    
- Maintain consistent card dimensions, spacing, and alignment across both tabs.
    

The distinction between Personal and Public should come from the content being displayed, not from different card designs.

### 5. Activity tab

Activity is a consolidated feed of interactions across everyone who has accessed a share link.

Aggregate activity from all share links, regardless of their original gallery location.

Include:

- Comments posted by visitors.
    
- Likes on shared files.
    
- Likes on comments.
    
- Interactions from all participating users.
    

Users must be able to like one another's comments, not just comments posted by the gallery owner.

The Activity tab should provide a unified view of activity across the entire sharing ecosystem.

### 6. Overall design objective

Personal, Public, and Activity should feel like three views of one cohesive application rather than separate gallery experiences.

Use the supplied screenshot as the visual reference. Preserve its minimalist, dark, iOS-inspired aesthetic and make the navigation, spacing, card proportions, and interaction patterns consistent throughout.

|`URL`|Gallery invitation URL|
|`STATUS:CONFIRMED`|Event status|
|`END:VEVENT`|End of event|

Use UTC timestamps or correctly formatted timezone-aware values to avoid discrepancies between devices and calendar platforms.

The event title must not expose:

- The underlying folder name.
    
- The original share-link name.
    
- Private gallery directory information.
    
- Other unnecessary personal information.
    

Use a neutral title such as:

**Gallery access**

The URL should take the guest to the actual gallery invitation, not directly to an unrestricted file or resource.

Ensure ICS text values are correctly escaped, URLs are properly encoded, and the generated file uses valid CRLF line endings and appropriate content folding.

Use the correct MIME type:

`text/calendar; charset=utf-8`

Provide a meaningful `.ics` filename and appropriate download headers.

## 12. Expiration and reminders

The calendar event's start and end times must reflect the actual invitation lifecycle.

Examples:

|Configured duration|DTSTART|DTEND|
|---|---|---|
|1 hour|Invitation creation|Creation + 1 hour|
|1 day|Invitation creation|Creation + 1 day|
|7 days|Invitation creation|Creation + 7 days|

Requirements:

- Start time equals the actual invitation creation timestamp.
    
- End time equals the actual invitation expiration timestamp.
    
- The event must not extend access beyond the actual expiration.
    
- Calendar reminders should help guests remember that access is temporary.
    
- Investigate appropriate `VALARM` support and reminder timing for different expiration durations.
    
- Do not schedule reminders after an event has already expired.
    
- Do not assume every calendar application handles alarms identically.
    

The calendar event is informational. It is not responsible for enforcing access expiration.

## 13. ICS security and lifecycle

Treat the invitation URL as a potentially sensitive credential.

Requirements:

- Use sufficiently strong invitation tokens.
    
- Do not embed email magic-link authentication tokens or session credentials in the ICS file.
    
- Do not expose private directory paths or internal database identifiers.
    
- Keep invitation access restrictions enforced server-side.
    
- Ensure expired invitations cannot be used, even if their ICS files remain on a device.
    
- Ensure revoked invitations immediately become unusable.
    
- Do not rely on calendar-event deletion to revoke access.
    
- Consider the implications of guests forwarding their ICS files or invitation URLs.
    
- Once an invitation has been claimed, require authentication appropriate to the established guest identity.
    

The ICS file must never become an alternative way to bypass authentication or invitation validation.

## 14. Calendar delivery and synchronization limitations

ICS is a portable calendar-event format, not a universal push-notification or calendar synchronization protocol.

The initial implementation should generate a downloadable ICS file.

The guest must be able to add/import the event into their preferred calendar.

After importing, synchronization across devices is handled by the guest's calendar provider.

Do not claim that generating an ICS file automatically inserts an event into someone else's calendar.

Do not introduce CalDAV, calendar-provider OAuth integrations, or custom calendar synchronization unless separately justified by a future requirement.
